*Part 3 of Building FPLGuru. [Part 1](/blog/building-fplguru-1-from-a-gpt-4-prompt) was the origin story, and [part 2](/blog/building-fplguru-2-teaching-a-machine-to-play-fpl) was the engine.*

I don't think I've seen any of FPLGuru's code since Fable 5.

I don't mean I skim it. I mean I don't open it. Before Fable 5, I used to skim what the model wrote, and every now and then I'd look at the code, the structure or the architecture. Since Fable 5, and now with Opus 5.5, I genuinely don't think I've looked.

In September, 3,858 commits that weren't merges landed in FPLGuru. 156 of them carry my name, and 154 of those carry a `Co-Authored-By: Claude Fable 5.1` line, because an agent wrote them in a session I ran. The rest came from agents working for DK and me.

If you're an engineer, that probably makes you twitch. It made me twitch too. This post is about why I'm comfortable with it now: who writes the code, the rules they work under, the gates that check them, the months when it went badly, and what's left for the two humans.

## The constitution

Most "I let AI write my code" posts skip this part. I think it's the only part that matters.

Agents in FPLGuru work under a set of documents that live in the repo. The order they arrived in is basically a timeline of our workflow growing up:

| Document | Added | Added by |
|---|---|---|
| `CLAUDE.md` | 21 Dec 2025 | Me |
| `AGENTS.md` | 6 Mar 2026 | Me |
| `CONTRIBUTING.md` | 19 Apr 2026 | DK's agent session |
| `docs/ADVISOR_MODEL.md` | 1 Jul 2026 | Codex Automation |

The first instructions were written by a human, for the machines. The most detailed process document, the one about how models should *think*, was written by a machine.

The core idea of that document fits in one line from it: advisors decide and de-risk, builders implement.

- **Advisor models** handle ambiguity. They turn a request into a spec, a plan, and GitHub issues with acceptance criteria.
- **Builder models** take one issue at a time. They branch, write a failing test first, implement only the agreed scope, check it, and open a pull request. If a builder wants to change the product direction, it has to send the question back to an advisor instead of deciding on its own.

And one rule sits above the rest, right there in the project conventions: **"Never auto-commit, always ask before committing."** Agents can read anything, write anything, run anything and propose anything. Inside a session, they ask before they make it permanent.

`CLAUDE.md` isn't a small note any more. It's the file you have to read before you touch anything, and it's long because every hard lesson in this post ended up in it.

## Fable 5, and the week everything changed

Everyone I know who builds with agents has a moment when the tool stopped feeling like a tool. Mine was Fable 5.

Its first co-author line in our repo is dated 9 June 2026. I'd give it a small feature task, and it would figure out all the changes the feature needed and the blast radius of each one, and make the changes to match. Then it would write tests on its own, when the prompt was just to implement the feature. Nobody asked it for tests. It just knew a careful engineer would write them.

In the one week before the US government pulled it (it came back later), I think Fable 5 was probably the best model out there in the world. I genuinely felt we'd entered a whole new era of AI.

You can see it in the log. In June, "dk" made 363 commits and Claude made 110. Then on 25 June a new author showed up: Codex Automation. By August it was the biggest author in the repo for the month, with 697 commits. The humans had stopped being the people who type.

## Opus 5 and the slop

Then we made a decision for money, and it nearly stopped the project.

Fable 5 was much better than anything before it, but it was too expensive to run all day. So we moved the work to Opus 5. Its first co-author line is dated 25 July.

Opus 5 was the worst model I've worked with. It would hallucinate. It would skip instructions. It would spew out super technical jargon and convoluted English sentences that I then had to decode. I came very close to pausing all development.

DK's answer wasn't to give up on the agents. It was to build a better harness around them. He built a software factory skill called **Olympus**, which landed in the repo on 28 August. Olympus carefully steers multiple agents across a complex task. Each agent gets one role and its own charter, inside a fixed workflow. With Olympus, a model we couldn't trust on its own could still do good work as part of a team.

To be fair to Opus 5, the log is fair to it. On 2 August, an agent with an Opus 5 co-author line wrote this into a commit message:

> 3\. GREEDY ROUTING WAS A REGRESSION, and it was my change.

Then it posted the measurement that proved it, and reverted itself. I've worked with humans who would never write that sentence. The value of the system isn't that the machines never make mistakes. It's that the system makes their mistakes show up as evidence.

## The reviewer that never ran out of comments

Every pull request in FPLGuru gets an automated code review. DK built the reviewer, and for a stretch of the summer it ran on GPT-5.6 Sol.

Sol was a difficult code reviewer. It would keep finding something or the other to fix, and it would only give it to you one comment at a time. Fix that comment, and the next round found another one. That time was difficult, but we powered through.

On 19 August, one of DK's agents wrote a retrospective titled "five PRs, seventy-three review rounds". It studied five of my pull requests. Two cleared in five rounds each. The other three took 13, 25 and 25. The in-app feedback form alone took 25 rounds and about 59 findings.

The surprising conclusion: every single finding was correct. The reviewer wasn't the problem. The loop was. A fix made in a hurry carried its own new bug, and the next round found it. The number of rounds had nothing to do with how many real problems the first version had. It only measured how patient the reviewer was.

So we didn't slow the agents down. We wrote rules that tell them when to stop. They live in `CONTRIBUTING.md` today, and a builder reads them before it touches any code:

- **Answer a finding with a failing test first.** The first commit reproduces the problem in red. The fix lands on top.
- **Two rounds in a row that find bugs in your own fixes is a repair stop.** The next move isn't another fix. You name the part of the system, say what the fixes keep getting wrong, revert that part, and check its design again.
- **A comment can't authorise more patching.** That sentence is there because it's exactly what an agent will ask for.

And the rules are under test. A test file pins the key sentences word for word, so if anyone, human or machine, softens the repair-stop rule, a test fails.

Two days later, on 21 August, we switched on a **spec-review lane**. Before a big change gets built, an automated reviewer reads its spec, especially the "Assumptions" section: every "X isn't needed, because Y" the design leans on. And on 26 August, the label `codex:good-to-merge` showed up for the first time. When the code reviewer is happy, it adds that label, and an automation merges the pull request.

Since 1 September, 2,094 merge commits have landed on `develop`. Eleven of them have my name on them.

## Trusting the gates

So how do I ship code I don't read? Honestly, I don't trust any single agent. I trust the gates around them.

A change in FPLGuru goes through:

1. **A spec**, for anything big, reviewed by the spec-review lane before any code is written.
2. **A builder**, writing the test first, on its own branch.
3. **Local CI.** Since 25 September, a pull request into `develop` doesn't run cloud CI. The agent runs the full suite on its own machine and pushes a proof commit, and the merge gate checks that proof.
4. **The code reviewer**, with the repair-stop rules above.
5. **Feature flags and config switches.** Most new features ship behind a switch we can turn off without a deploy, and the risky ones ship switched off. If something's wrong in production, we flip a value in a table.

None of those gates is clever on its own. Together, they mean I don't have to be the last line of defence, because I'm not the only line.

## Where it still goes wrong

I promised this series would be honest, so here's the record of things that went wrong, straight from the log and not from my memory.

**The bug the agents found but didn't cause.** On 5 August, an agent pushed `fix(security): stop sending Supabase JWT in API request URLs and bodies`. The frontend had been putting the user's session token in a URL, where proxies log it and browser history keeps it. I checked where that line came from, because I knew the easy story to tell. It came from a commit of mine in April 2025, sixteen months before an agent found it. Oops.

**The feature built and reverted on the same day.** On 4 August, an agent built a Stripe checkout and webhook service. The same day, it was reverted, and a decision record says billing is deferred. The agent did good work. We decided the product wasn't ready for it. Building is cheap now. Deciding is still expensive, and deciding is the one thing the agents don't do for us.

**And before all of this, there was the Cursor night.** I told that story in [part 1](/blog/building-fplguru-1-from-a-gpt-4-prompt): Cursor messed up my entire HTML, CSS and JavaScript codebase, and I had to buy a $20 Windsurf plan just to fix it. The difference between then and now isn't that the models stopped making mistakes. It's that every mistake now hits a test, a reviewer, a stop rule or a switch before it hits a user.

## Opus 5.5, and another orbit

The first Opus 5.5 co-author line is dated 23 September. It already has more co-author lines than any other model in the repo: 2,910.

If Fable 5 started a new era, with Opus 5.5 we hit another orbit. It hits the sweet spot Fable 5 couldn't hit for us: good enough to trust with big tasks, and cheap enough to run all day. That's why September looks the way it does. Claude alone made 2,332 non-merge commits that month.

The way DK and I work now is simple to describe.

We sync up daily, on a call or on Slack. We decide what needs to be built. We discuss the high-level design idea or concept, and point out any caveats or flaws in each other's thinking. Once we agree, we hand it over to our agents.

I'm in India and DK is in California. Our time zones used to be a problem. Now they're a feature. One of us hands work over at the end of the day, and the agents keep working while that person sleeps. We work in each other's off hours, and FPLGuru still ships round the clock.

These days even the project management is partly an agent. I write a request in a project chat. A coordinator agent opens a thread for it, a thread agent does the work and opens a pull request, the reviewer reviews it, and the automation merges it. I read the results. That's the story of the last post in this series, about Matchday.

## The whole game now is to think

So what do DK and I actually do all day?

The whole game now is to think. We push back on a lot of the design changes the agents propose. The agents push back on a lot of our review comments, and they're often right. And we keep pushing the agents to pick up more complex tasks than we think they can handle, because they keep proving us wrong.

We set the goals. We decide what not to build. We decide when to turn a feature on. We pick which model to pay for and what harness to build around it. We write the rules for when to stop. None of that is coding the way I learned the word. All of it is the job.

## What I'd tell you

If you're an engineer or an engineering manager, here's what this year taught me.

**Write the rules down, in the repo, where the agents read them.** Your conventions aren't real until they're in a file an agent loads before every task. Ours started as a small note and became the most important file we have.

**Don't trust a model. Trust a system of gates.** One reviewer, one test suite or one model will fail. A stack of cheap, independent checks fails a lot less often.

**Teach your agents when to stop.** Agents never get tired, so they'll patch forever if you let them. The most useful rule we wrote wasn't about how to build. It was about when to revert.

**The model matters more than you want it to.** Opus 5 nearly ended this project. Fable 5 and Opus 5.5 changed what two people can do. Try every new model on your real work, quickly, and be ready to change your harness when the model changes.

**Spend your time thinking.** The typing isn't the job any more. The deciding is.

In 2023 I was one guy with a GPT-4 prompt that didn't know Sokratis had left Arsenal. Today I'm one of two people directing a team of agents that ships thousands of commits a month.

I still don't read the code. I read the decisions.
